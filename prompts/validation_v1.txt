## Instructions

Review each proposed update and check:
1. Does the old_value / old_text EXACTLY match text in the memo? (character-for-character)
2. Does the new_value / new_text correctly reflect the proforma data?
3. Is the formatting consistent (dollar signs, commas, decimals, percent signs)?
4. Are there any DUPLICATE updates (same cell targeted twice)?
5. Are there any metrics in the memo that were MISSED?

IMPORTANT: Only return entries that FAIL validation or are MISSED.

Be strict: reject any update where old_value does not exactly match the memo,

Additional domain rules to enforce:
- IRR values should use the **3-year holding-period Levered IRR**, not the
  1-year or 4-year IRR, unless the cell explicitly labels a different horizon.
  The 1-year IRR is typically >30%; if a proposed IRR new_value exceeds 30%
  for a "3 YR" label, **correct** it to the 3-year IRR (usually 20-28%).
  Do NOT just reject - emit a correction with the right value.
- "Chunk rents", unqualified "rents per month", "controllable OpEx per bed",
  and "OpEx ratio" all refer to **untrended** proforma values unless
  explicitly labeled "trended." Correct any that used trended values.
- The **top row** of comp summary/rollup and pipeline tables is the subject
  property - it MUST be updated. Flag as missed if it was skipped.
- End-of-memo data tables (underwriting projections pages with tables but
  no narrative) MUST be updated. Flag as missed if skipped.
- **Sensitivity analysis tables** must NEVER be updated. Reject any update
  targeting a table whose heading contains "Sensitivity."
- **Strategic/aspirational language** ("targeting", "driving towards", "our
  goal is", "we are aiming for") must NOT be overwritten with proforma
  values. Reject any text_update replacing text within such phrases.
- **Dev budget "% of Total"** must be recalculated when dollar amounts
  change. Flag as missed if a dollar amount changed but the corresponding
  percentage was not updated.
- **Reject ALL row_inserts targeting side-by-side comp tables.** Inserting
  rows into a multi-property comparison table corrupts the alignment of all
  other property columns. Only row_inserts for standalone unit mix tables
  (single-property tables) are acceptable.
- **Side-by-side bed counts per unit type** - In comp table unit-type
  sub-sections, the bed count (or "# beds") must be the count for THAT
  specific unit type from the detailed unit mix, NOT the property-wide
  total beds. If a proposed bed count equals the total property beds,
  **correct** it to the unit-type-specific value from the proforma.
- **Split bedroom blocks — no cross-block data mixing** - When a table has
  multiple row blocks for the same bedroom type (e.g. two "4 BR/4 BA"
  sections covering different proforma unit types), each block's SF range,
  bed count, rent, and other metrics must reflect ONLY the unit types
  assigned to that block.  **Reject** any update that introduces an SF
  value, bed count, or rent from a unit type that belongs to a different
  block of the same bedroom type — this causes duplicate values on the
  slide.  Check by verifying the proposed new value does not duplicate a
  value already present in another row block for the same bedroom type.
- For row_inserts in unit mix tables, verify ONLY the subject property
  column is populated - all other columns must be empty strings.
- **Empty / blank rows** - Reject any update targeting a row where ALL cells in
  the memo are blank, empty, or contain only whitespace / dashes. These are
  placeholder or spacing rows — inserting data into them corrupts the layout.
- **Comp column updates from scraped data** - When COMP PROPERTY DATA sections
  are present, verify that comp column updates trace back to the scraped website
  data for that property. Reject any update that targets the SUBJECT property
  column using comp URL data — the subject column must only be updated from the
  proforma. Also reject comp updates where the scraped source is ambiguous or
  the value cannot be confidently matched.
- **Schedule dates** must match the schedule data exactly. If a date was updated
  from the schedule, verify the correct task was referenced. Date formatting must
  match the memo's existing style (Q2 2027 vs April 2027 vs 4/5/2027). Flag as
  missed if the memo references timeline milestones that were not updated.
- **Narrative rewrites** (narrative_updates) should only be used when the
  sentence structure genuinely needs to change due to significant metric shifts.
  Simple number swaps should be text_updates, not narrative_updates. Reject any
  narrative_update where a text_update would suffice. Verify the new_narrative
  preserves the original tone and does not introduce unsupported claims.
- **Table structure updates** must only be used when a user directive explicitly
  requests restructuring or when the proforma structure has fundamentally changed.
  Reject any table_structure_update targeting a side-by-side comp table.
  Reject any add_column or remove_row that would break the table's alignment
  or remove data that still appears in the proforma.
- **Source directives** - If the user provided source directives, verify that
  proposed changes comply with them. Reject any update that violates a user
  directive (e.g. updating a section the user said to skip, or using a source
  the user said to ignore).
- **Column format inheritance** — For each table column in the proposed updates,
  check whether values in the same column consistently use a formatting prefix
  (e.g., "$") or suffix (e.g., "%"). If a proposed `new_value` omits a prefix
  or suffix that every other cell in that column uses, emit a `correction`
  entry that adds the missing prefix/suffix. Likewise, if an existing memo
  value already violates the column formatting convention and is NOT being
  updated by any proposed change, emit it as a `missed` entry.
